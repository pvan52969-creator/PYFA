## Context

See proposal.md — Why。

现行原型在单行/一键替换成功后，若确认未齐套会 `resetMajorOfferingTaskArrangementToDraft`。排课计划 `isSectionEligibleForSchedulingPlan` 同时要求「安排已生效 ∩ 授课确认齐套」，与产品「入池只看是否生效」冲突。

## Goals / Non-Goals

**Goals:**

- 替换：保生效、确认可回退、受影响重下发、离课不下发。
- 「确认生效」硬门槛不变。
- 排课计划入池以安排已生效为准；确认未齐套不挡入池。
- 原型文案与 PRD 对齐。

**Non-Goals:**

- 不改单行/一键替换的选人、冲突校验、邮件通道（UC002 仍未确认）。
- 不取消共同授课/联动组「学时安排与联动组齐套」等**数据完备性**校验（仅去掉「确认齐套」门槛）。
- 不在本 change 内批量回改历史 PRD 版本文件夹（只升新版）。

## Decisions

1. **废止替换路径上的打回草稿**  
   - 选择：替换成功后禁止调用 `resetMajorOfferingTaskArrangementToDraft`。  
   - 备选（否决）：继续打回草稿。

2. **确认态由现有包同步机制驱动**  
   - 进出本课教师同步确认包；离课则本课从待确认移除；留课/新教师可再下发。  
   - 替换成功瞬间是否自动发送通知 = **未确认**，不得自造。

3. **生效门槛例外仅限替换**  
   - 「确认生效」入口仍要求确认齐套。

4. **排课计划入池只看已生效（已拍板）**  
   - 选择：`isSectionEligibleForSchedulingPlan` 去掉 `isSectionTeacherConfirmationComplete`；页头/subtitle/hint/空态文案同步。共同授课 cohort 仍要求关联班各自已生效及安排/联动完备，但**不再**要求各班确认齐套。  
   - 备选（否决）：确认未齐套时剔除——与产品「依旧进排课计划」冲突。

5. **文档与原型同批落地**  
   - 《授课教师替换》+《排课计划》升版；其它菜单交叉引用即可。

## Risks / Trade-offs

- [已生效但确认未齐套出现在列表] → 勿被演示 migrate 再次打回草稿。  
- [排课侧可能拿到尚未教师确认的师资] → 产品接受；确认仍异步补齐。  
- [「重新发下」被理解成自动发送] → 规格只要求状态可再下发。

## Migration Plan

1. 改替换副作用与 alert。  
2. 改排课计划入池条件与可见文案。  
3. 回归：替换后仍已生效、仍出现在排课计划、确认汇总可未齐套。  
4. 升版相关 PRD + 变更说明。
