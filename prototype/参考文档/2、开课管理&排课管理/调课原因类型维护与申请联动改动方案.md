# 调课管理 · 调课原因类型（二级菜单）维护与申请联动改动方案

> 文档性质：代码改动方案（需求文档，供实现前对齐）  
> 适用范围：  
> 1. 调课管理（管理端）→ **调课原因类型**（唯一维护菜单，建议放在「调课申请管理」前）  
> 2. 教师端「我的调课申请」/ 管理端代申请 → `#modal-adjustment-apply` 仅使用已启用原因（无维护页）  
> 3. 调课申请详情 / 审批详情回显  
> 关联代码：`prototype/index.html`、`prototype/app.js`、`prototype/styles.css`  
> 状态：**已按确认口径实现**

---

## 1. 改动目标

在「调课管理」下增加**唯一一条**二级菜单「调课原因类型」，**仅管理端维护**。教师端没有维护页、也不再挂一条同名菜单；教师（及代申请）只在发起申请时使用**已启用**的原因类型。

固定内置一条 **Academic-Related**：

- 选中后必须选择**请假记录**；
- 该教师无请假记录时，提示：  
  **请先提交 Academic-Related Travel / Leave Application Form，再申请调课**；
- 切换任意原因类型时，选择器下方展示该类型的**附件说明**。

非目标（本期不做，除非确认）：

- 不改批量调课、公假日停课的事由字段。
- 不新建真实「Travel / Leave Application Form」业务页；请假记录用原型 mock（见 §5）。
- 不改排课表时间 / 排课表教室两侧。
- 不做原因类型多级树（父/子原因）；本页是扁平字典，「二级」指侧栏二级菜单。

## 2. 现状摘要

### 2.1 导航

侧栏「调课管理」现有二级项（`index.html`）：

```text
我的调课申请
调课申请审批
调课申请管理
调课申请记录
公假日停课
批量调课管理
```

尚无原因类型维护页。`SCHEDULE_PAGE_IDS` 亦未登记对应 page-id。

### 2.2 申请弹窗原因

`#modal-adjustment-apply` 右侧已有：

| 控件 | DOM | 现状 |
| --- | --- | --- |
| 原因类型 | `#adjustment-apply-reason-type` | 必填下拉 |
| 申请事由 | `#adjustment-apply-reason` | 必填文本 |
| 附件 | `#adjustment-apply-files` | 可选上传 |

选项来自硬编码：

```js
const ADJUSTMENT_REASON_TYPES = ['因公出差', '学术会议', '培训进修', '学院安排', '生病请假', '其他'];
```

填充：`ensureAdjustmentReasonTypeOptions()`。  
提交：`submitAdjustmentApply()` 校验非空后写入 `request.reasonType`。  
详情：展示 `r.reasonType`（缺省走 `inferAdjustmentReasonType`）。

**没有**：附件说明联动、按调课类型/教师类型过滤、请假记录、启用开关。

### 2.3 教师类型

申请人档案 `getAdjustmentApplicantProfile().teacherType` 来自花名册 `staffType` / `teacherType`。  
枚举与开课教师类型一致：`TEACHER_TYPE_CODES`（`AC (CS)`、`PT`、`RE (F)` 等）。

调课类型：`ADJUSTMENT_TYPE_META` → `reschedule` / `cancel` / `makeup` / `addclass`。

原型内**无**请假 / Travel Form 数据。

## 3. 维护页：调课原因类型

### 3.1 入口

| 项 | 建议 |
| --- | --- |
| 菜单 | **只做一条**：调课原因类型 |
| 位置 | 「调课管理」下，与管理端页放一起（建议紧挨「调课申请管理」之前） |
| page-id | `adjustment-reason-type` |
| 页面 | `#page-adjustment-reason-type` |
| 管理端 | 唯一维护入口：增删改、启用/停用 |
| 教师端 | **无此菜单、无维护页**；只在「我的调课申请 → 发起××」弹窗里选已启用原因 |

`SCHEDULE_PAGE_IDS` 增加 `adjustment-reason-type`；`showPage` 分支调用 `renderAdjustmentReasonTypePage()`。

### 3.2 列表

查询（建议）：原因类型关键字、是否启用、适用调课类型。操作：查询 / 重置 / **新增**。

| 列 | 说明 |
| --- | --- |
| 序号 | |
| 原因类型 | 名称；Academic-Related 可加「固定」标记 |
| 附件说明 | 过长截断，hover 看全文 |
| 适用调课类型 | 调课 / 停课 / 补课 / 加课，顿号拼接；空=全部 |
| 适用教师 | 教师类型代码拼接；空=全部教师类型 |
| 是否启用 | 启用 / 停用 |
| 操作 | 修改；非固定可删除（二次确认） |

### 3.3 新增 / 修改弹窗字段

| 字段 | 控件 | 规则 |
| --- | --- | --- |
| 原因类型 | 文本 | 必填；同名不可重复（忽略大小写）；固定项只读 |
| 附件说明 | 多行文本 | 可空；申请端选中后展示原文 |
| 适用调课类型 | 多选勾选 | 调课 / 停课 / 补课 / 加课；**不选 = 全部适用** |
| 适用教师 | 多选勾选 | 选项 = `TEACHER_TYPE_CODES`；**不选 = 全部教师类型** |
| 是否启用 | 开关 | 默认启用；停用后申请下拉不出现 |

固定项 **Academic-Related**：

- `code` 固定为 `academic-related`，不可删除、不可改名；
- 允许改附件说明、适用调课类型、适用教师、是否启用；
- 「必须选请假记录」由代码按 `code === 'academic-related'` 判断，**不做可配开关**（避免关掉后申请端丢失校验）。

### 3.4 数据（建议）

```js
ADJUSTMENT_REASON_TYPE_STORE = {
  seq: n,
  items: [
    {
      id, code, name,
      attachmentHint,          // 附件说明
      applyTypes: [],          // ['reschedule','cancel',...] 空=全部
      teacherTypes: [],        // TEACHER_TYPE_CODES 子集，空=全部
      enabled: true,
      builtin: false           // Academic-Related 为 true
    }
  ]
}
```

种子：

1. **Academic-Related**（`builtin: true`，启用）  
   - 附件说明建议：`Please attach the approved Academic-Related Travel / Leave Application Form.`  
   - 适用调课类型 / 适用教师：空（全部）
2. 将现有 6 条中文原因迁入为可编辑种子，避免演示单、旧下拉断层。

`ADJUSTMENT_REASON_TYPES` 字符串数组改为从 Store 读名称；`inferAdjustmentReasonType` 仅服务历史单，不参与新下拉。

修改记录：`registerEntityChangeLogMeta('adjustment-reason-type', …)`，字段对齐上表。

## 4. 申请弹窗联动

教师端、代申请共用 `#modal-adjustment-apply`，只改原因区，不改左右栏选节次。

### 4.1 下拉过滤

`ensureAdjustmentReasonTypeOptions()` 改为按当前上下文过滤：

| 条件 | 口径 |
| --- | --- |
| 启用 | `enabled === true` |
| 调课类型 | `applyTypes` 为空，或包含当前 `adjustmentApplyType` |
| 教师类型 | `teacherTypes` 为空，或包含当前申请人 `teacherType` |

申请人：

- 教师端：`getAdjustmentApplyApplicantId()`  
- 代申请：当前「代申请教师」；**换教师后重刷**原因下拉、附件说明、请假记录。

打开弹窗、切换代申请教师时重算。已选值若不在新列表中则清空，并收起说明 / 请假区。

### 4.2 附件说明（所有原因类型）

在 `#adjustment-apply-reason-type` **正下方**增加提示区，建议 id：`#adjustment-apply-reason-hint`。

- 未选：隐藏  
- 已选且有附件说明：展示该说明  
- 已选但说明为空：隐藏（不占位）

`onchange` → `syncAdjustmentApplyReasonTypeUI()`。  
样式：选择器下小字提示（可用现有 `.text-muted`），与附件上传区那句「支持上传…」分开：前者跟原因类型走，后者仍是通用上传帮助。

### 4.3 Academic-Related → 请假记录

选中 `academic-related` 后，在附件说明与「申请事由」之间插入：

```text
请假记录 *  [下拉]
```

建议 id：`#adjustment-apply-leave-record`，外层 `#adjustment-apply-leave-wrap`。

| 情况 | 交互 |
| --- | --- |
| 有**已批准且与调课申请时间重叠**的请假记录 | 下拉必填；选项见 §5 |
| 该教师没有任何已批准请假记录 | 下拉隐藏或禁用；展示：<br>**请先提交 Academic-Related Travel / Leave Application Form，再申请调课** |
| 有已批准记录，但无一与当前调课申请时间重叠 | 下拉为空；提示无与本次调课时间重叠的请假记录，禁止提交 |
| 切到其他原因 | 收起请假区、清空已选 |

「调课申请时间」= 当前草稿已选节次的日期跨度（与申请单 `applyStart` / `applyEnd` 同一套 `collectAdjustmentDraftTimePoints`）。请假 `[startDate, endDate]` 与该跨度有交集即算重叠。选节次 / 改日期后重刷请假下拉。

提交 `submitAdjustmentApply()` 增补：

1. 原因仍为 Academic-Related，且无已批准请假记录 → `alert` 先提交 Form 文案，拦截；  
2. 有记录但与调课时间无重叠 → 拦截并提示无重叠请假记录；  
3. 有重叠记录但未选 → `alert('请选择请假记录')`，拦截。

写入申请单：

```text
reasonType          // 展示名 Academic-Related
reasonTypeCode      // academic-related
leaveRecordId
leaveRecordLabel    // 冗余快照，详情不依赖 mock 是否还在
```

打开弹窗时清空请假选择（与原因类型一并 reset）。

### 4.4 详情 / 列表

请假记录**只在申请详情 / 审批详情**展示（原因类型下一行），列表「事由」列不加请假。  
演示种子单不必强行改成 Academic-Related；实现后可用一条新演示单覆盖详情回显。

## 5. 请假记录 mock

本期不接真实请假系统，在调课模块内造演示数据。

建议 `ADJUSTMENT_LEAVE_RECORD_STORE`：

| 字段 | 说明 |
| --- | --- |
| id | |
| teacherId | 与花名册工号一致 |
| formNo | 如 `AR-2026-001` |
| kind | `Travel` / `Leave` |
| startDate / endDate | |
| status | 下拉只出 `approved` |

选项文案建议：`AR-2026-001 · Travel · 2026-03-01 ~ 2026-03-05`。

演示建议：

- 至少 1 名常用演示教师（如当前默认申请人）有 1～2 条已批准记录，便于测必填选择；

`listAdjustmentLeaveRecords(teacherId, { start, end })`：该工号、已批准，且日期与调课申请时间重叠。

## 7. 交互流程（申请）

```text
打开申请弹窗
  → 按调课类型 + 教师类型填充原因下拉
选择原因类型
  → 下方展示该类型附件说明（有则显示）
  → 若为 Academic-Related
        有重叠请假记录 → 显示请假下拉（必填）
        无任何已批准记录 → 提示先提交 Travel / Leave Form，禁止提交
        有记录但不重叠 → 提示无重叠请假记录，禁止提交
提交
  → 原因类型必填；Academic-Related 必须已选与调课时间重叠的请假记录
```

## 8. 已确认口径

1. 菜单**只做一条**「调课原因类型」，挂在管理端（与「调课申请管理」同组）。教师端不做维护页、不挂第二条菜单；教师只在申请弹窗使用已启用原因。原型侧栏目前教师/管理页列在一起，该项按管理页放置，不在「我的调课申请」下复制。  
2. 适用调课类型 / 适用教师**不选 = 全部**。  
3. Academic-Related 固定不可删、不可改名；请假必填写死在该 `code` 上。  
4. 旧 6 条中文原因迁入 Store，避免演示数据与下拉断裂。  
5. **任一原因类型停用**（含 Academic-Related）后，教师/代申请的原因下拉**不显示**该项。  
6. 请假下拉只出：该教师、已批准、且日期与**调课申请时间重叠**的记录。  
7. 请假记录**只在详情页**回显，列表不加列。  
8. 附件说明**只做提示**，不改为必须上传附件。  
9. 批量调课、公假日停课不接本字典。

## 9. 原待确认项（已收口）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 「第一点」是哪个页面、教师能否维护 | **一个管理端维护页**：调课管理 → 调课原因类型。教师端仅使用已启用原因（申请下拉），不做页面维护、不加菜单。 |
| 2 | 停用后申请端是否消失 | **是**。Academic-Related 或任何原因类型停用 → 申请下拉不出现 |
| 3 | 请假是否与调课日期重叠 | **要重叠**。下拉过滤 + 提交校验 |
| 4 | 列表是否加请假列 | **否**，只在详情页显示 |
| 5 | 附件说明是否必须上传 | **否**，只做提示 |

## 10. 自检

- 只测维护页：能增改删（固定项除外）；停用任一条后，申请下拉立刻少该项。  
- 只测教师申请：下拉随调课类型 + 本人教师类型变化；换原因只更新下方附件说明（提示，不强制上传）。  
- 选 Academic-Related 且有重叠请假：不选不能提交。  
- 选 Academic-Related 且无已批准请假：看到指定 Form 提示，不能提交。  
- 有请假但不与本次调课日期重叠：下拉为空，不能提交。  
- 详情能看到请假记录；列表看不到。  
- 代申请换教师：原因列表与请假区跟着变。  
- 排时间 / 排教室两侧行为与改前一致。
