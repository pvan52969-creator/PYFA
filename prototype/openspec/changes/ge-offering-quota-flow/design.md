# 通识选修开课 · 需求 / 配额 / 学院消化（方案 A）

## Context

- 现有模块：校选课程管理 → 通识选修开课计划（手工加课）→ 任务安排 → 名单管理。
- 真实业务：执行计划修读要求 → 学期需求参考 → AC 定组数下限 → 学院开课消化 → 任务/名单（开放选课由选课应用落人）。
- 方案 A：少改后半段，先补需求看板 + AC 配额，再把计划页挂上配额约束。

## Goals / Non-Goals

**Goals**

- 原型可演示：需求参考 → AC 配额 → 学院 ≥ 下限开课 → 任务/名单。
- 明确「组数下限 + 每组人数参考值」语义；超额无需确认。
- 需求文档可标注正式联动点（执行计划修读要求），原型用假数据。

**Non-Goals**

- 严格从执行计划实时汇总（正式开发做）。
- 学院级文商理（学院不具有文商理类别，挂专业）。
- 选课算法、名单自动分配规则。
- 任务安排/合班等专业开课能力迁移到 GE。

## Decisions

### D1 · 信息架构（方案 A）

```
通识选修课开课
├─ 通识选修开课需求        ← 新（只读参考 + mock）
├─ 通识选修小组配额        ← 新（AC）
├─ 通识选修开课计划        ← 改（配额进度 + 下限校验）
├─ 通识选修开课任务安排    ← 保留
└─ 通识选修课开课名单管理  ← 保留
```

需求也可作为配额页顶部只读区复用同一数据源；菜单仍保留独立入口，方便讲故事。

### D2 · 文商理与交叉规则

| 维度 | 归属（当前） | 用途 |
|------|-------------|------|
| 学生侧大类 | **专业** → arts / business / science | 需求汇总、交叉可选范围 |
| 课程侧大类 | 校选课 `geCategory` | 开课计划筛选与展示 |

学院本身不具有文商理类别；配额按学院定保底组数，不带文商理字段。

交叉修读（原型文案与校验提示用）：

- 文科学生 → 可选 **商科、理科** GE（不可同大类）
- 商科学生 → 可选 **文科、理科** GE
- 理科学生 → 可选 **文科、商科** GE

### D3 · 配额语义

- AC 为每个学期维护：
  - 文/商/理 **总组数**（统筹目标，可选展示）
  - 各学院 **保底组数 minGroups**（**下限**）
  - **每组人数参考值** `refGroupSize`（教务备注定，如 40；用于需求→组数建议与容量默认参考）
- 学院实际开组数 `actualGroups`：**必须 ≥ minGroups**；可多开，**超额不需 AC 确认**。
- 「可分配组数有限制」在业务上表述为 **下限约束**，不是上限硬顶。若产品文案曾写「限制」，UI 统一为「保底组数 / 下限」。
- 本模块管：**组数** + **每组人数上限（capacity）**；名单由选课应用生成。

### D4 · 需求数据（原型 vs 正式）

**正式开发**

1. 读取已提交/锁定的专业批次执行计划。
2. 看执行计划详情 Tab「选修类分类 · 修读要求」（4 学年 × 3 学期矩阵），判断本开课学期该批次是否要求修 GE。
3. 汇总：批次列表、预计总人数、分学院、分文商理（按学院映射）。

**原型**

- `GE_OFFERING_DEMAND_MOCK`：按学期给一批假批次/人数即可推进后续配额与开课。
- 需求页注明：「演示数据；正式环境来自执行计划修读要求」。

### D5 · 学院开课计划改造

- 顶部摘要：本学期需求要点 + **本校配额进度**（已开组数 / 下限；可超额显示为绿色达标）。
- 加课流程不变（校选课库）；加组/设容量时显示参考人数。
- 提交计划前：若该学院 `actualGroups < minGroups` → 阻止提交并提示差几组。
- 1 门课多组 / 多门课 1 组均允许；只累计组数。

### D6 · 与后半段边界

```
配额/计划（供给）          选课应用（需求落地）
─────────────────         ─────────────────
开几组、每组人数上限   →   学生选课进组/进名单
任务安排：教师/学时    →   （排课等后续）
名单页：可微调演示     →   正式以选课结果为准
```

## Data Model（原型）

```text
GE_OFFERING_QUOTA_BY_TERM[termCode] = {
  termCode,
  refGroupSize,                    // 每组人数参考值
  categoryTotals: { arts, business, science }, // AC 定的大类总组数（展示/校验合计用）
  colleges: [
    { schoolCode, stream, minGroups }  // stream 来自学院→文商理映射
  ]
}

GE_OFFERING_DEMAND_MOCK[termCode] = {
  termCode,
  totalStudents,
  bySchool: [{ schoolCode, stream, students, batches: [...] }],
  byStream: { arts, business, science },
  crossRuleNote: '...'
}

专业 → stream 映射（见 PROGRAMME_GE_STREAM_MAP）
PROGRAMME_GE_STREAM_MAP = { CHS/ENG/…: arts, ACC/FIN/…: business, CST/AIT/…: science }
```

`actualGroups`：从本学期已加入计划的 GE sections 的 `groups.length`（或计划阶段约定的拟开组数）汇总；若计划阶段尚无 groups，可用 section 上的 `plannedGroupCount` 字段（原型可加）。

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| 学院文商理映射变更 | 单点改 `SCHOOL_GE_STREAM_MAP`；看板按 stream 聚合 |
| 计划阶段无真实 groups | 增加 `plannedGroupCount`，任务安排落组后回写对齐 |
| 需求假数据与执行计划不一致 | 页面明确「演示」；正式需求写进 spec 备注 |
| 总组数与学院下限之和不一致 | 配额页保存时提示合计 vs 大类总组数（可警告不强制） |

## Migration

- 无历史生产数据；现有 GE 计划行保留，补默认配额 mock，使演示学院已达标或差 1～2 组以便演示校验。
