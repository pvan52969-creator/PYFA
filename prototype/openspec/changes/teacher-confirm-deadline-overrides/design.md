## Context

See `proposal.md` — Why。

现行实现要点：

- 开课时间设置按学期维护全校 `teacherConfirmDeadline`（仅日期）。
- 教师端确认信 Notes 经 `getTeacherCourseConfirmationDeadlineIso(termCode)` **只读全校值**。
- 同页已有「单位开课时间」：全校窗口 + 所属部门覆盖（可晚于全校）。**交互可借鉴，语义不可混用。**
- PRD 仍把「超过授课确认截止日期是否锁定」标为未确认；当前原型不过期拦截确认。

教师确认维度是 **教师 × 学期**（一封信），Notes 只有一个 `before <date>` 槽位——因此生效截止日必须收敛为**每个教师一个日期**，不能按课拆多日期。

## Goals / Non-Goals

**Goals:**

- 给出可落地的分层模型与解析规则，使学院/专业「适当延迟」可配置、可审计。
- 教师信函展示生效日；管理端可见来源层级。
- 原型可先做「全校 + 学院 + 个人例外」；专业层作为可选扩展，规格上预留。

**Non-Goals:**

- 本设计不实现硬锁定确认（过期禁操作）；仅预留字段语义，待产品拍板。
- 不按单门课各自截止日拆信。
- 不把授课确认截止并入「单位开课时间」同一字段。

## Decisions

### D1 — 推荐分层：全校默认 → 学院 →（可选）专业 → 个人例外

```
学期全校默认 teacherConfirmDeadline
        │
        ├─ 学院/所属部门覆盖（日常主路径，对标客户「学院延迟」）
        │
        ├─ 专业覆盖（可选；仅当学院内专业节奏明显不同时启用）
        │
        └─ 个人延期（例外；教务对单人下发，须填原因）
```

优先级（从高到低）：**个人 > 专业 > 学院 > 全校**。取最高优先级已配置的绝对日期为生效日。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A 仅全校 | 现状 | 简单 | 客户已说不够 | 保留作底 |
| B 全校+学院 | 对齐单位开课时间 | 覆盖「学院延迟」主诉求，维护量可控 | 专业差异靠个人/再扩 | **v1 推荐** |
| C 全校+学院+专业 | 完整组织树 | 精细 | 专业×学期配置面大，教师跨专业难解释 | 规格预留，二期 |
| D 直接到人为主 | 每人一日期 | 最灵活 | 不可运营 | 仅例外 |

**Alternatives considered：** 用「代确认」代替改截止日期——**否决**。客户要的是发给老师的日期可变，不是事后由管理员代点确认。代确认仍是无法自助操作时的辅助手段，与截止日分层无关。

### D2 — 解析锚点：教师所属部门，而非开课单位

一封信对应一名教师，Notes 只能写一个日期。

- **采用：** 以教师主数据 **所属部门（学院/单位）** 匹配学院覆盖；若有专业覆盖，以教师主专业（或人事专业）匹配。
- **不采用：** 按本学期所授课程的开课单位取 max/min——跨学院兼课会导致「同人不同课不同日」，信函无法表达，管理端催办也乱。

跨单位兼课：仍用所属部门覆盖；若需更晚，走**个人延期**。

### D3 — 覆盖形态：绝对日期（可晚于全校）

- 覆盖存 **绝对日期**（与全校字段同形态），不用「+N 天」。
- v1 校验：**学院/专业/个人截止日 ≥ 全校默认**（只许延迟，不许收紧）。收紧需求走改全校日或另议。
- 删除覆盖后回退到下一优先级。

**Alternatives considered：** `+N 天` 相对偏移——全校改日时自动平移，但对账不直观、与现有日期控件不一致；v1 不做。

### D4 — 维护入口与权限

- 全校日：仍在学期「新增/修改开课时间」（教务）。
- 学院覆盖：开课时间设置 →「单位开课时间设置」展开表中，在「开放截止」右侧「授课确认截止」列行内编辑（与开课窗口同表，勿另开独立入口）。未填则沿用全校。
- 个人延期：授课确认管理「个人延期」打开管辖范围内教师名单（随页面所属部门筛选）；勾选后批量设置/清除个人截止日（无延期原因）；教师×学期一条，覆盖该人本学期全部确认任务。
- **权限（已确认）：** 教务管理员与学院秘书**都可以**维护学院覆盖与个人延期（学院秘书范围限本学院教师/本单位）。

### D5 — 展示与效力（给客户的建议口径）

客户当前是在问「有没有好办法满足学院/专业适当延迟」，**不是**先要系统过期锁死。

| 场景 | 建议口径 |
|------|----------|
| 教师信 Notes | 展示**对该教师生效的截止日** |
| 管理端 | 展示生效日 + 来源（全校/学院/个人） |
| 过期后 | 与截止日分层无关；首版仍不锁死自助确认 |
| 代确认 | **不解决「信上日期要变」**；仅保留为教师无法操作时的辅助 |

## Risks / Trade-offs

- [学院覆盖按所属部门] → 开课单位与所属部门不一致的教师可能「感觉不对」→ 说明规则 + 个人延期兜底。
- [只许延迟] → 学院不能设比全校更早 → 要收紧就改全校日。
- [先不做硬锁] → 截止日偏沟通/进度工具 → 符合客户当前「要建议、不要先上锁」的诉求。
- [专业先不做] → 专业差异用「学院覆盖 + 少量个人延期」顶一阵 → 例外变多再加专业层。

## Migration Plan

1. 存量学期仅有全校日 → 无覆盖时行为与现在一致。
2. 新增覆盖配置；Notes/管理端统一走解析结果。
3. 回滚：去掉覆盖即回到全校日。
