## Context

专业开课任务安排 style2 已具备分组、师资安排与「生效」操作；`teachingConfirmStatus` 字段曾存在但语义与「任务安排已提交/生效」缠绕，且缺少按教师下发、教师确认/不同意的独立流程。历史上学校通过线下邮件确认（`参考文档/Template for Course Confirmation Letter.docx`）；**现改为系统内确认**，不再发邮件。入口期望：分组工作台视角 Tab、Teaching Load 点教师名跳转，以及可单独打开的确认管理/确认页面。

利益相关方：教务（下发确认、代确认、看诉求、改安排、重新下发、生效）、授课教师（系统内确认或不同意并写诉求）。部分教师因年龄、设备原因无法自行操作，教务需代确认并留痕。本变更为原型站实现，演示闭环即可。

## Goals / Non-Goals

**Goals:**

- 以**教师 × 学期**汇总待确认授课安排，支持**系统内下发 / 重新下发**确认任务。
- 确认页展示与原确认函一致的信息字段；**Total Student No. = 课程人数上限**。
- 教师在系统内确认或不同意（必填诉求）；教务可查看诉求并在调整安排后重新下发。
- **管理端代确认**：教务可替教师确认，须标记「管理端代确认」及操作人、时间。
- style2「生效」仅在该开课任务相关授课教师**全部已确认（含代确认）**后可用。
- 分组工作台新增 Tab；Teaching Load 教师名可跳到该教师确认管理视图。

**Non-Goals:**

- 邮件发送、校园邮箱集成、确认函 PDF/Word 导出（原模板仅作字段参考）。
- 通识选修、特殊开课确认链路（后续扩展）。
- 专业开课计划页「生效」语义改造（本变更只卡住任务安排 style2 生效）。
- 与旧 `teachingConfirmStatus` 全局语义大清洗（仅在本流程内定义清晰的教师确认态，避免误伤其他页）。

## Decisions

### 1. 确认粒度：教师 × 学期（一次确认多门课）

- **选择**：一次确认任务覆盖该教师在本开课学期内、已纳入下发范围的全部授课行；行级展示 Course Code / Name / Classification / Credits / Teaching Weeks / Lecture·Lab 组数 / Total Student No. / Weekly Hours / Coordinator / Co-teaching。
- **理由**：与原确认函「Academic Session」维度一致；教务按教师催确认更自然。
- **备选**：按开课任务（section）逐条确认 — 拒绝，因业务入口与汇总均为教师维度。

### 2. 下发范围与「相关教师」定义

- **选择**：某开课任务的「授课教师」= 该 section 当前师资安排中所有已指派教师（含共同授课）。对该 section「生效」时，要求这些教师在**当前确认轮次**上均为 `confirmed`（含代确认）。
- **下发**：教务从授课确认管理页对某教师下发本学期安排快照；也可从某 section 上下文提示未确认教师。
- **备选**：仅主讲需确认 — 拒绝，用户要求「授课教师都确认」。

### 3. 状态模型（教师确认记录）

按 `teacherId + termCode` 维护确认包（package），内含课程行快照与状态：

| 状态 | 含义 |
|------|------|
| `draft` / 未下发 | 有安排但尚未下发确认任务 |
| `pending` | 已下发，待教师或管理端处理 |
| `confirmed` | 已确认本轮快照 |
| `disagreed` | 教师不同意并填写了诉求 |

确认方式（`confirmed` 时必填）：

| 值 | 含义 |
|----|------|
| `teacher` | 教师本人在系统内确认 |
| `admin-proxy` | 管理端代确认（列表/详情展示「管理端代确认」标记，记录操作人与时间） |

- 调整该教师相关安排并**重新下发**后：状态回到 `pending`，清空旧确认，保留历史诉求与代确认记录供查看。
- section 级「教师确认齐套」= 当前指派教师均存在本学期 `confirmed` 且快照仍匹配当前安排（安排变更未重新下发则视为未齐套）。

### 4. 系统内确认 vs 原邮件流程

- **选择**：全流程在系统内完成——下发即写入 `pending`，教师登录（或原型角色切换）后在确认页操作；**不发送邮件**。
- **原模板**：仅作为确认页应展示哪些字段的历史参考，不还原邮件正文、抄送、附件等形态。
- **备选**：保留「发信」UI 模拟邮件 — 拒绝，用户明确不需要邮件。

### 5. 管理端代确认

- **选择**：教务在授课确认管理页可对 `pending` 状态的教师执行「代确认」；须二次确认并记录 `confirmedBy: admin-proxy`、`proxyBy`（操作人）、`confirmedAt`。
- **展示**：style2 进度、教师列表、确认详情均须能区分「已确认」与「管理端代确认」（如 pill / 标签）。
- **理由**：部分教师年龄、设备原因无法自行操作；代确认须可审计。
- **备选**：代确认不计入齐套 — 拒绝，代确认与本人确认同等满足生效门槛。

### 6. 与「生效」门槛的关系

- **选择**：在现有「分组/教师/学时完备」校验之上，增加「教师确认齐套」；未满足时「生效」按钮禁用或二次确认拦截，提示未确认教师名单。
- **不**把教师确认等同于任务已生效；确认是生效前置，生效仍是教务显式操作。

### 7. 页面与入口

| 入口 | 行为 |
|------|------|
| 分组工作台 Tab「授课确认」 | 教务：按学期看教师列表、下发/重新下发、代确认、查看诉求与状态 |
| Teaching Load 点教师名 | 跳到该教师在确认管理视图的聚焦态 |
| 教师确认页（原型角色切换或直链） | 教师查看安排、确认 / 不同意 |
| style2 列表 | 展示确认进度（如 2/3 已确认，含代确认标记）；生效受门槛约束 |

### 8. Total Student No.

- **选择**：取 `getSectionCapacityLimit(sec)`（课程人数上限）。
- **不**用计划人数或当前名单人数。

### 9. 不同意闭环

```
教师 disagree + 诉求
    → 教务在授课确认 Tab 查看诉求
    → 进入分组/师资安排调整
    → 对该教师重新下发确认（新快照）
    → 教师本人确认 或 管理端代确认
    → 全部确认后教务可「生效」
```

重新下发前若安排未变，允许重新下发但应提示；安排已变则必须重新下发后才计入齐套。

## Risks / Trade-offs

- [旧 `teachingConfirmStatus` 语义冲突] → 新流程使用独立的教师确认包状态；section 上仅衍生「齐套」只读标记或复用字段时加注释隔离。
- [安排微调导致大量需重确认] → 仅当该教师相关行变更时重置该教师确认态；未波及教师保持 confirmed。
- [代确认滥用] → 操作记录与「管理端代确认」标记留痕；原型可简化为 alert 二次确认。
- [共同授课行字段复杂] → Co-teaching 列展示同课其他教师姓名（演示数据）；缺省显示 —。

## Migration Plan

- 原型：启动时为演示学期注入若干「已安排未下发 / 待确认 / 已确认 / 代确认 / 不同意」样例。
- 已「生效」的演示任务可保持生效，或重置为未生效以便演示门槛（实现时选一种并在 tasks 注明）。
- 回滚：移除 Tab/页面与生效额外校验即可，不影响分组数据结构。

## Open Questions

- 教师确认页在原型中的登录态：建议用现有角色/演示切换模拟「当前教师」，实现时采用最简方案。
- 下发是否必须覆盖该教师本学期**全部**专业开课安排，还是允许按学院过滤 — 默认全部专业开课；若需学院过滤，实现前再定。
