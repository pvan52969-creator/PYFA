## Why

师资安排完成后，开课任务目前可直接「生效」，缺少授课教师对本学期授课安排的正式确认。历史上学校曾通过线下邮件确认（见 `参考文档/Template for Course Confirmation Letter.docx`），现已有系统，应改为**系统内确认**完成闭环。业务上需先按教师维度下发确认任务，待相关授课教师全部确认后，才允许将该开课任务生效；教师若不同意，教务需查看诉求、调整安排并重新下发确认。部分教师因年龄或设备原因无法自行操作，管理端应支持**代确认**并打上特殊标记。

## What Changes

- 新增**授课教师确认**能力：以**教师 × 开课学期**为维度汇总并**系统内下发**本学期授课安排确认任务（不再通过邮件发送）。
- 确认页展示字段沿用原确认函的信息维度（课程号/名称/类别/学分/教学周/组数/Total Student No. 等）；**Total Student No. = 课程人数上限**。
- 教务侧可在独立入口**下发 / 重新下发**确认；分组工作台视角 Tab 增加入口；Teaching Load 中点击教师名可跳转到该教师的确认管理视图。
- 教师侧提供确认页：可**确认**，或**不同意并填写诉求**（均在系统内完成）。
- **管理端代确认**：教务可替教师完成确认，记录须标记为「管理端代确认」（含操作人、时间）；列表与进度中可区分教师本人确认与代确认。
- **不同意闭环**：教务查看诉求 → 调整教师/学时安排 → **重新下发确认** → 教师或管理端再次确认。
- 专业开课任务安排 style2 的「生效」增加门槛：**该开课任务下所有授课教师均已确认（含代确认）**后方可生效。
- 本阶段范围：**专业开课 · 任务安排 style2** 链路；通识/特殊开课后续再扩。

## Capabilities

### New Capabilities

- `teacher-course-confirmation`: 授课教师确认全流程（按教师系统内下发、确认内容展示、教师确认/不同意、管理端代确认标记、诉求回看与重新下发、任务「生效」前教师确认齐套门槛）

### Modified Capabilities

- （无）`openspec/specs/` 下暂无已归档主规格需改写

## Impact

- `index.html` / `app.js` / `styles.css`：新增确认管理页、教师确认页、分组工作台 Tab、导航入口；style2「生效」校验与状态展示
- Teaching Load / 教师名跳转：`#modal-offering-teacher-term-assign` 及相关渲染
- 数据模型：教师确认记录（待下发/待确认/已确认/不同意+诉求、确认方式 teacher|admin-proxy、操作人与时间）、与 section/教师安排的关联；重新下发后重置该教师相关确认态
- 演示数据与操作记录（下发、确认、代确认、不同意、重新下发）
- 参考：原邮件模板仅作字段语义参考，不实现邮件发送或函件导出
