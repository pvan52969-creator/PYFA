## Goals / Non-Goals

**Goals:**

- 15 份菜单文档齐套（13 升版 + 2 首版）：每份含 PRD md/docx + 变更说明 md/docx
- 内容对齐客户确认版：界面树、字段矩阵（含 Add/Edit/View）、功能 F、规则 BR、数据流；差异写入变更说明对象 ID
- 首版菜单建立 `03_选修开课/01_选修开课计划`、`03_选修开课/03_选修开课名单` 目录

**Non-Goals:**

- 不改 `app.js` / `index.html` 交互（文档交付）
- 不出培养方案 / 排课 / 调课 PRD
- 不出侧栏注释菜单（特殊开课三菜单、合分班与明细）
- 默认不出「操作流程图」独立 PRD
- 不把变更说明写成迷你 PRD

## Decisions

1. **范围锁死为「开课管理可见侧栏」而非整门户**  
   - Rationale：仅此处有 V3.1 目录规范与脚本；培养方案/排课无同等流水线，一次做完会空壳交差。  
   - Alternative：整门户全量 → 否决为本变更默认；可作二期 change。

2. **一律新建版本文件夹升版，禁止覆盖 20260909/10 现行最高版**  
   - Rationale：与 `prd-versioning-change-notes` 规范一致；客户确认交付需可回溯。  
   - Alternative：原地覆盖（数据来源回填那次例外）→ 否决。

3. **真源优先级：侧栏可见 UI > 已确认 OpenSpec 已落地行为 > 旧 PRD 文字**  
   - Rationale：用户明确「根据当前版本」；旧 PRD 仅作 ID 延续与变更对照。  
   - Alternative：以旧 PRD 为主微调 → 否决（会漏确认后改动）。  
   - 已知须落入本轮对照的确认点（非穷尽）：教师替换后安排保持已生效；授课确认期限个人/学院覆盖；授课确认管理 Co-teaching 列；选修计划/安排/名单合页现状。

4. **ID 策略：沿用上一版 P/FD/F/BR 编号；新增对象续号；删除对象在变更说明标删除**  
   - Rationale：便于变更说明「对象 ID」列与研发对照。  
   - Alternative：每版重编 ID → 否决（断裂追溯）。

5. **实施顺序：脚手架 → 开课设置 3 → 专业开课 3 → 选修开课 3（含 2 首版）→ 课程班管理 6**  
   - Rationale：设置/专业已有厚基线；选修首版风险高；课程班含近期确认点放后便于一次对照。  
   - Alternative：15 份并行一次交 → 易漏、难评审。

6. **docx：md 定稿后用既有规范化/模板填充脚本出 docx；变更说明用 `generate-submenu-prd-change-note.py`（默认 V3）**  
   - Rationale：与历史批次一致，避免手改 docx 漂移。  
   - Alternative：只交 md → 否决（交付惯例要 docx）。

7. **「无差异不升版」门禁**  
   - Rationale：规范写明无实质变更勿升版。实施时若某菜单与上一版逐节一致，跳过并在 tasks 勾掉并注明。  
   - 预期：确认后多菜单有实质差，多数仍会升版。

## Risks / Trade-offs

- [工作量大 / 易漏 tip→BR] → 每菜单 checklist：界面树 → 主表/筛选项 → 弹窗/抽屉 → tip/alert 扫 BR → 数据来源列  
- [选修首版无旧 ID] → 按 V3.1 新编；变更说明写无→V1 总览  
- [特殊开课页代码仍在、侧栏注释] → 文档范围以侧栏为准，避免「客户未在导航确认」的菜单出 PRD  
- [培养方案/排课被理解为「所有菜单」] → proposal 已标非目标；实施前若用户改口再扩 scope  
- [OpenSpec 未完成 change（elective-module-gap-audit 等）与确认版冲突] → 以可见原型为准；未落地交互不写入已确认需求

## Migration Plan

1. 更新 `prd_folder_paths`（若缺选修计划/名单路径说明）并建空二级目录  
2. 按批次写新版本文件夹：PRD md → 变更说明 md → 生成 docx  
3. 抽检：每份变更说明对象 ID 能在新 PRD 找到；数据来源无「原型」字样；未确认项有 UC  
4. 回滚：删除未验收的新版本文件夹即可，不碰旧版
