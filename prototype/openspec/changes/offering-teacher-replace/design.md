## Context

专业开课任务安排 style2 展开后的「开课安排详情」面板（`offering-grouping-global-assign-panel`）展示 `section.groupAssignments` 行：小组、学时类型、起止周、学时、教师、同时授课、教室属性/偏好等。任务「生效」后 `schedulingVisible === true`（且计划已提交），分组工作台进入只读，教务无法再走常规「安排教师」改人。

用户需要：在「开课清单」下独立菜单，专门对**已生效**开课，按**安排明细的某一整行**替换授课教师；明确不能只换某些周次。

既有可复用能力：教师选择器（`#modal-major-teacher-picker` / group-assign 同源）、Teaching Load 汇总、授课教师确认（`teacher-course-confirmation`）、开课变更类日志模式（如 section change log）。

## Goals / Non-Goals

**Goals:**

- 「开课清单」下「授课教师替换」入口与列表页
- 仅列出已生效开课任务；进入后展示该课安排明细行
- 对单行执行整行教师替换（覆盖该行 `teachers`，其它列不变）
- 写入可追溯替换记录；替换后与确认态/学时统计保持一致可读

**Non-Goals:**

- 未生效任务的师资编辑（仍用分组工作台）
- 按周次拆行换人、或只改行内部分周
- 一次替换多门课、或跨 section 批量换同一人
- 改排课冲突检测算法、自动重排课表
- 本阶段不重做共同授课码维护 UI

## Decisions

### 1. 入口与信息架构

- **选择**：侧栏「开课清单」下新增 `data-page="course-offering-teacher-replace"`，文案 **「授课教师替换」**；页面 id `page-course-offering-teacher-replace`。
- **备选**：挂在任务安排 style2 行内操作 — 否决，用户明确要清单下独立菜单，且已生效场景与日常安排入口分离更清晰。

### 2. 「已开课生效」判定

- **选择**：与现网一致：`submitStatus === 'submitted'` 且 `schedulingVisible === true`（展示为「已生效」）。列表默认当前开课学期，可筛课号/开课单位。
- **首期范围**：以**专业开课**为主；通识选修若同判定为已生效则**同页可并列展示**（用开课类型列区分），特殊开课模块当前已下线则不纳入。
- **备选**：仅 style2 演示课 — 否决，业务入口应对全体已生效专业开课。

### 3. 明细与操作粒度

- **选择**：进入某 section 后，明细表对齐 style2 展开面板列（至少：序号、课程班/小组、学时类型、起止周、周学时、总学时、教师、同时授课）；每行操作 **「替换教师」**。
- **整行替换语义**：将该 `groupAssignments` 行的 `teachers`（及行上派生的教师展示字段）整体换成所选新教师集合；**不**修改该行的 `weekRange` / 学时类型 / 周学时 / 总学时 / 同时授课 / 教室字段；**不**把一行拆成多行按周换人。
- 若原行有多名教师（共同授课行）：本阶段默认 **整组替换为选择器确认的教师集合**（选择器可多选时与既有安排教师一致；若当前选择器单选，则替换为主讲一人并清掉同行其它人 —— 在实现时与现有 picker 能力对齐，并在页内 hint 说明）。
- **备选**：只替换「主讲」、保留 Support — 否决为首版默认；若行内角色需保留，可在 Open Questions 确认后迭代。

### 4. 教师选择器

- **选择**：复用既有专业开课教师选择器（单位 = 开课单位 + 已申请 Support），替换场景下 context 标记 `mode: 'replace-assignment-row'`，确认后写回目标行而非新建安排。
- **备选**：新建简化姓名输入 — 否决，需工号/类型/学院与 Teaching Load 一致。

### 5. 确认态与下游

- **选择**：替换成功后：
  1. 更新 section 安排行；
  2. 追加替换日志；
  3. 若存在授课教师确认记录：对新教师该 section **重置为待确认（或待下发）**，旧教师与该行相关的确认项标记失效或归档；页内提示「替换后需重新下发/确认」。
- **备选**：替换不碰确认态 — 否决，会导致「已确认」与实际师资不一致。
- Teaching Load：依赖现有从 `groupAssignments` 汇总，替换后刷新即可，无需单独算法。

### 6. 替换日志

- **选择**：内存 + localStorage 日志，字段示意：`{ id, termCode, sectionId, assignmentRowId, code, courseName, groupLabel, hourType, weekRange, fromTeachers[], toTeachers[], operatedAt, operator }`。页内可提供「最近替换记录」折叠区或简单列表，不必另开菜单。
- **备选**：写入既有 section change log — 可并存；首期独立 store 更轻，避免改既有日志筛选语义。

### 7. 演示数据

- **选择**：确保至少 1～2 个已生效专业开课 section 带有多行 `groupAssignments`（可复用 MPU3113 / OCE101 展示课），便于替换前后对照。

## Risks / Trade-offs

- [整行替换多人行时角色丢失] → 页内说明；若业务要保留 Support，后续加「按角色替换」。
- [替换后未重下发确认] → 列表/详情提示未确认；生效已完成不再回退生效态，仅要求确认闭环。
- [与分组工作台只读冲突] → 本页是唯一允许改已生效师资的入口；工作台仍只读。
- [用户误以为可按周换人] → 操作文案与确认弹窗明确「整行起止周内教师一并替换，不可按周拆分」。

## Migration Plan

- 无历史库迁移；原型刷新后新菜单可用。
- 回滚：隐藏导航与页面即可；替换已写入的 section 数据需手工还原或依赖演示重种子。

## Open Questions

- 多人共同授课行：首版是「整组换成新选择集合」，还是「只换指定一人、其余保留」？（默认整组替换，实现前若产品有异议再改 tasks。）
- 替换后是否强制立刻弹出「重新下发确认」？（默认仅提示，不强制弹窗。）
