## Context

见 `proposal.md`。用户已确认按计划默认假设实施（真源=可见 UI+已明确规则；升版不覆盖；深度=状态/字段/BR/实体；优先级 P0→P2）。

## Goals / Non-Goals

**Goals:**

- 十二菜单各产出 `20260902V(n+1)` PRD md+docx + 变更说明 V3
- 跨菜单状态与实体对照短文
- P0 优先保证：计划/安排/名单、授课确认两端、教师替换规则可编码

**Non-Goals:**

- OpenAPI / 物理表 DDL
- 改业务代码
- 权限矩阵最终拍板（可保留未确认，禁止 AI 猜测）

2. **状态口径（写入对照短文与各 PRD）**  
   - 计划生效：`draft` / `submitted` / `reverted`（UI「生效状态」）  
   - 安排生效：含 `cancelled`（停课）及与授课确认、`taskArrangementSubmittedAt` 的关系按原型描述  
   - 授课确认：教师包状态与班级 `teachingConfirmStatus` 分列，禁止混用  

3. **开课安排 UI**：2 步条；查询区有学期/课号等（对齐原型）

4. **教师替换**：按原型写「替换后未齐套 → 打回草稿 + 需重新确认」（已明确对照原型）

5. **产出脚本**：`scripts/generate-prd-backend-ready-20260902.py`（禁止覆盖已有版本目录）

## Risks / Trade-offs

- [Risk] 列表列极多导致文档膨胀 → Mitigation：列表区全列必写；表单可分节，禁止「以弹窗为准」单行占位  
- [Risk] 权限未拍板 → Mitigation：显式「后端禁止自造」  
- [Risk] 演示规则被当成校政 → Mitigation：标注「演示规则」
